Building REST APIs That Don't Rot

A personal journey from messy first APIs to maintainable, evolvable systems — and the principles that got me there.

Z

Zwelibanzi Langeni

11 min read
LinkedIn X Copy Link

The First API I Built

I still remember the weekend I built my first REST API. I had just discovered Spring Boot, and the sheer thrill of spinning up a web server with a few annotations felt like magic. I wrote my first @RestController, mapped a couple of endpoints, and watched Postman return JSON responses with a sense of triumph. I was twenty-two, caffeinated, and utterly convinced I had mastered backend engineering.

That API was supposed to be a simple user management service for a side project. I packed everything into a single controller — validation, business logic, database queries, even some half-baked error handling. It worked perfectly on my machine, and I deployed it with a grin. I thought I had built something solid.

Looking back, that API was a textbook example of what happens when excitement outpaces experience. But I didn't know that then. All I knew was that I had built something that worked, and that felt like enough.

When My API Started Rotting

Fast forward eight months. A friend wanted to collaborate on the project, so I dusted off the codebase and opened the controller file. My jaw tightened. The class had grown to over six hundred lines. There were duplicate methods, inconsistent naming, and a sprawling switch statement that routed requests based on query parameters. I couldn't tell which endpoint did what without tracing through the entire file.

The worst part? I couldn't blame anyone else. I had written every single line.

"Every API is a promise to your future self."

That was the moment I realised my API had rotted. Not because of a single catastrophic failure, but because of hundreds of tiny shortcuts I had taken in the name of shipping quickly. I had told myself I'd refactor later. Later never came.

Adding a new feature took forever. Changing existing behaviour risked breaking something unrelated. The tests I had written were brittle and covered only the happy path. I felt like I was walking through a minefield every time I touched the code.

That experience was a turning point. I realised that building an API that works today is easy. Building an API that still works — and is still pleasant to work with — a year from now is the real challenge. I became obsessed with understanding why software rots and what I could do to prevent it.

Five Principles That Changed Everything

Over the next few years, I read voraciously. I studied the codebases of open-source projects I admired. I refactored my old projects over and over, learning something new each time. Gradually, a set of principles emerged — principles that transformed how I think about API design.

These aren't the usual SOLID or Clean Architecture platitudes, though those are important too. These are the practical, battle-tested lessons I've carried from project to project, the ones that have saved me from myself more times than I can count.

Keep Controllers Thin

The first rule I adopted is almost embarrassingly simple: keep your controllers thin. A controller should be a thin veneer over your application logic — it parses the request, delegates to a service, and constructs a response. That's it. No business logic, no database access, no complex validation beyond basic request validation.

Here's what a well-behaved controller looks like in Spring Boot: 

@RestController
                                    @RequestMapping("/api/v1/users")
                                    @Validated
                                    public class UserController {

                                    private final UserService userService;

                                    public UserController(UserService
                                    userService) {
                                    this.userService = userService;
                                    }

                                    @GetMapping("/{id}")
                                    public ResponseEntity<UserResponse>
                                    getUser(@PathVariable Long id) {
                                    return ResponseEntity.ok(userService.getUser(id));
                                    }

                                    @PostMapping
                                    public ResponseEntity<UserResponse>
                                    createUser(@Valid @RequestBody CreateUserRequest
                                    request) {
                                    UserResponse response =
                                    userService.createUser(request);
                                    return ResponseEntity.status(HttpStatus.CREATED)
                                    .body(response);
                                    }

                                    @PutMapping("/{id}")
                                    public ResponseEntity<UserResponse>
                                    updateUser(
                                    @PathVariable Long id,
                                    @Valid @RequestBody UpdateUserRequest
                                    request) {
                                    return ResponseEntity.ok(userService.updateUser(id,
                                    request));
                                    }

                                    @DeleteMapping("/{id}")
                                    public ResponseEntity<Void>
                                    deleteUser(@PathVariable Long id) {
                                    userService.deleteUser(id);
                                    return ResponseEntity.noContent().build();
                                    }
                                    }

Look at how little is happening in that controller. It maps HTTP verbs to service methods, applies validation, and returns appropriate HTTP status codes. All the interesting work — the business logic, transaction management, and domain rules — lives in the service layer.

This separation has saved me countless times. When I need to change how user creation works, I touch the service. When I need to change the API contract — maybe add a new endpoint or change the response structure — I touch the controller. These concerns stay neatly separated, which means changes are localised and the risk of unintended side effects drops dramatically.

Think in Resources

REST is about resources. I know that sounds obvious, but it's surprisingly easy to forget. I've seen countless APIs that are really just RPC calls dressed in REST clothing — endpoint names like /api/activateUser or /api/processOrder that scream "procedure call" rather than "resource manipulation".

The shift in thinking is subtle but profound. Instead of designing endpoints around actions, design them around nouns. What resources exist in your system? What operations make sense on those resources?

For a user management system, the resource is a User. The operations are create, read, update, and delete. For an e-commerce system, resources might include Order, Product, and Customer. Each resource gets its own URI space, and HTTP methods express the action.

This resource-oriented thinking forces you to model your domain explicitly. It reveals hidden concepts and relationships. And it makes your API predictable — developers who understand REST can intuit how your API works without reading extensive documentation.

One of my favourite examples of getting this right is the GitHub API. It's resource-based through and through. You work with repositories, issues, pull requests, and comments as first-class resources. The consistency makes the API feel coherent and discoverable.

Consistency Beats Cleverness

I used to be clever. I'd use @JsonView to return different fields based on the user's role. I'd nest resources five levels deep because it seemed elegant. I'd use query parameters to overload endpoints with multiple behaviours.

I don't do that anymore.

Clever solutions are often the ones that cause the most pain later. They're surprising, non-obvious, and hard to remember. When you come back to the codebase six months later, you spend twenty minutes trying to understand why the same endpoint returns different fields for different users.

Instead, I now favour boring, consistent conventions. Here's what that looks like in practice:

  • Naming: Use plural nouns for collections ( /api/v1/users), singular for specific resources ( /api/v1/users/{id}). Use kebab-case for multi-word resources ( /api/v1/order-items).
  • HTTP methods: GET for retrieval, POST for creation, PUT for full updates, PATCH for partial updates, DELETE for deletion. Never use GET for state-changing operations.
  • Status codes: 200 for success with a body, 201 for creation, 204 for success without a body, 400 for client errors, 404 for not found, 500 for server errors. Be consistent about when you use each.
  • Error responses: Use a standard error envelope with fields like timestamp, status, error, and path.

The goal is to make your API predictable. A developer who has worked with one of your endpoints should be able to guess how the others work. This reduces the cognitive burden of adopting your API and makes it feel professional and polished.

Consistency also extends to your codebase. Use the same patterns for validation, logging, and exception handling across all your controllers. If you use @Valid on one endpoint, use it on all of them. If you log requests in one place, log them everywhere. The cumulative effect of these small consistencies is a codebase that feels cohesive and well-crafted.

Design for Tomorrow

One of the hardest lessons I learned was that APIs are forever. Once you release an API and clients start depending on it, changing it becomes a negotiation. You can't just delete a field or rename an endpoint because you think the new name is better. You have to support the old version while introducing the new one.

This is why versioning matters. I used to avoid versioning because it felt like extra work. I'd just evolve the API in place and hope no one noticed. That strategy worked exactly zero times.

Today, I version my APIs from day one. I put the version in the URL path: /api/v1/users, /api/v2/users. This is explicit and easy for clients to understand. It also gives me a clean mechanism for deprecating old versions gradually.

But versioning isn't just about the path. It also means thinking about how your API will evolve. What fields might you need to add? What operations might become more complex? Designing with future growth in mind doesn't mean over-engineering — it means leaving room for change.

One pattern I've found useful is the expandable contract. Instead of returning a fixed set of fields, consider supporting field selection via query parameters: /api/v1/users/42?fields=id,name,email. This allows clients to request exactly what they need and gives you flexibility to add new fields without breaking existing clients.

Another strategy is to use API evolution guidelines. Document how you'll handle breaking changes, how long you'll support old versions, and what the deprecation process looks like. This sets clear expectations and reduces friction when you need to make significant changes.

Documentation Is Part of the Product

I used to think documentation was an afterthought. I'd write the code, deploy it, and then maybe jot down some notes in a README. I treated documentation as a chore, something to be done grudgingly after the real work was finished.

Then I started using other people's APIs. I discovered how frustrating it is to work with an API that has no documentation, or worse, documentation that's inaccurate or out of date. I realised that documentation is not a luxury — it's a core part of the product.

Today, I use OpenAPI (formerly Swagger) to document my APIs. I generate the specification from the code using annotations like @Operation and @ApiResponse. This keeps the documentation in sync with the code and produces a machine-readable specification that can be used to generate client SDKs, API explorers, and interactive documentation.

Here's a simple example of a documented endpoint: 

@Operation(summary = "Get a user by ID",
                                    description = "Returns the user with the specified ID,
                                    including profile information and preferences.")
                                    @ApiResponses(value = {
                                    @ApiResponse(responseCode = "200", description =
                                    "User found", content = @Content(mediaType =
                                    "application/json", schema = @Schema(implementation
                                    = UserResponse.class))),
                                    @ApiResponse(responseCode = "404", description =
                                    "User not found"),
                                    @ApiResponse(responseCode = "401", description =
                                    "Unauthorized")
                                    })
                                    @GetMapping("/{id}")
                                    public ResponseEntity<UserResponse>
                                    getUser(@PathVariable Long id) {
                                    return ResponseEntity.ok(userService.getUser(id));
                                    }

The annotations add context that helps clients understand the endpoint's behaviour, expected inputs, and possible responses. But the real value comes from the OpenAPI specification itself. With a spec, I can:

  • Generate an interactive API explorer that lets developers try out endpoints in their browser.
  • Generate client SDKs for multiple languages so clients don't have to write HTTP requests manually.
  • Validate that my API conforms to the specification, catching errors early.
  • Use the spec as a contract for integration testing.

Documentation is also where you communicate your API's personality. A well-written description, a clear error message, a thoughtful example — these small touches make the API feel cared for. They signal to users that you've thought about their experience.

Building APIs That Age Gracefully

The goal, ultimately, is to build APIs that age gracefully. APIs that don't become brittle and tangled as the codebase grows. APIs that remain easy to understand, easy to change, and easy to trust.

The secret, I've learned, is to embrace change rather than resist it. Software rots when it becomes rigid. When you stop refactoring, stop improving, stop learning. A healthy codebase is one that changes constantly — not because it's unstable, but because it's evolving to meet new needs.

Refactoring is not a sign of failure. It's a sign of maturity. I refactor my code constantly now, not because it was wrong the first time, but because I understand the problem better now than I did when I wrote it. Each refactor is an opportunity to make the code simpler, clearer, and more maintainable.

One practice I've adopted is the boy scout rule: leave the codebase cleaner than you found it. When I touch a file, I look for small improvements I can make — renaming a variable, extracting a method, adding a comment. These micro-refactors accumulate over time and keep the codebase from decaying.

I also pay attention to architectural boundaries. Clean Architecture, Hexagonal Architecture, Onion Architecture — they all share a common insight: keep the core domain independent of external concerns. The business logic should not depend on the database, the web framework, or the messaging system. This independence makes it easier to change external dependencies without rewriting the core logic.

For my REST APIs, this means keeping the domain model separate from the API contract. The User entity in the database is not the same as the UserResponse DTO returned by the API. I map between them in the service layer, which gives me the freedom to evolve the domain model without breaking the API contract.

Testing, Learning, and Staying Curious

I want to talk about testing because it's where I've changed the most. In my early days, I wrote tests for the sake of coverage. I'd mock everything, write assertions that verified the mock interactions, and declare victory. I didn't really understand what I was testing or why.

Today, I approach testing differently. I write tests that verify behaviour, not implementation. I test the API as a whole, using @SpringBootTest with TestRestTemplate or WebTestClient. I test the important flows — successful requests, validation failures, error scenarios, authentication and authorisation. These integration tests give me confidence that the API works correctly end-to-end.

I also write unit tests for the service layer, focusing on the business logic. These tests are fast and targeted. They mock the repository layer and verify that the service behaves correctly for different inputs.

Contract testing has been a revelation. I use spring-cloud-contract to define contracts between my API and its consumers. The contracts are written in Groovy or YAML and used to generate both server-side tests and client-side stubs. This ensures that changes to the API don't break consumers — and that consumers are using the API correctly.

"Good architecture isn't about adding layers. It's about removing friction."

The most important part of this journey, though, is staying curious. I've learned more from reading other people's code and experimenting with new ideas than from any tutorial. I build side projects to test concepts. I rewrite old projects using new approaches. I contribute to open-source projects to see how other people solve problems.

Curiosity is what keeps the craft alive. Without it, you stagnate. You repeat the same patterns, make the same mistakes, and never grow. With it, every project becomes an opportunity to learn something new.

Final Thoughts

Building REST APIs that don't rot is not about a single tool or technique. It's about a mindset. It's about caring deeply about the quality of the code you write. It's about respecting the people who will work with your code in the future. It's about understanding that software is never finished — it's always evolving.

I've been building APIs for years now, and I still make mistakes. I still write code that I later regret. But I've also learned to recognise the signs of rot early, to refactor before the debt becomes unmanageable, and to design with maintainability as a first-class concern.

If I could go back and give my younger self one piece of advice, it would be this: your API is a promise to your future self. Write code that you'll be proud to come back to. Write code that you'll be able to understand and change without dread. Write code that ages gracefully.

That's what building REST APIs that don't rot really means. It's not about perfection — it's about intention. It's about building with care, learning from mistakes, and always, always striving to be better.

The journey never ends, and that's exactly why I love it.
