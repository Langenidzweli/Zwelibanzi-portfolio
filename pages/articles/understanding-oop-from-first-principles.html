Understanding OOP from First Principles

A personal journey through the foundations of Object-Oriented Programming — not as a set of rules to memorise, but as a way of thinking about code, data, and the problems we solve.

Zwelibanzi Langeni

The First Time I Met OOP

I still remember my first encounter with Object-Oriented Programming. It was a university lecture, and the professor drew a diagram of a Car class with color and model attributes, then a startEngine() method. It seemed almost trivial. I nodded along, wrote the code in my IDE, and promptly forgot about it.

For the next two years, I wrote code that was technically OOP — I used classes, objects, and inheritance — but I never really understood why. I treated OOP as a syntax requirement rather than a way of thinking. My classes were anemic data bags; my inheritance hierarchies were deep and brittle; my code was procedural code draped in class declarations.

It took a failed project, a humbling code review, and many late nights of refactoring before I began to grasp what OOP was truly about. It wasn't about extends or implements. It was about modelling the world in a way that made software feel alive, flexible, and understandable. This is the story of how I unlearned and relearned OOP from first principles.

The Problem OOP Was Built to Solve

To understand OOP, we have to step back to the 1960s. Software was growing larger and more complex. Procedural languages like FORTRAN and COBOL worked well for mathematical calculations and business reports, but they struggled with maintaining state across many functions, and they made it difficult to reuse code effectively.

The core insight behind OOP was simple but radical: data and behaviour belong together. A BankAccount doesn't just have a balance; it has operations for depositing and withdrawing that are intimately tied to how the balance is maintained. If you separate the data from the behaviour, you end up with functions scattered everywhere, each one needing to know the internal structure of the data.

This separation is what leads to spaghetti code. When a change to a data structure requires updating dozens of functions, the code becomes fragile. OOP's answer was to bundle data and behaviour into cohesive units called objects, and to expose only what was necessary through interfaces. This wasn't just a technical decision — it was a cognitive one. It made software easier for humans to reason about.

"OOP is not about the language. It's about how you organise your thinking."

Over time, I realised that OOP isn't the only way to model software. Functional programming has its own strengths. But OOP remains incredibly powerful for domains where stateful interactions are central — which is most business applications. The key is to understand the why behind the features, not just the how.

Encapsulation: The Art of Hiding What Matters

My first real lesson in OOP came from encapsulation. I had a class representing a User with a field passwordHash. I naively made it public. Later, when I needed to change the hashing algorithm, I had to search through the entire codebase to find every place that accessed that field directly. It was a mess.

Encapsulation taught me that the internal state of an object is nobody's business but its own. The object should expose a controlled set of methods through which external code can interact. This is the principle of information hiding.

Here's how I would write a User class today: 

public class User {
                                    private final Long id;
                                    private String email;
                                    private String passwordHash;
                                    private boolean active;

                                    public User(Long id, String email) {
                                    this.id = id;
                                    this.email = email;
                                    this.active = true;
                                    }

                                    public String getEmail() {
                                    return email;
                                    }

                                    public void changeEmail(String newEmail,
                                    PasswordValidator validator) {
                                    if (!validator.isValid(newEmail)) {
                                    throw new IllegalArgumentException("Invalid
                                    email");
                                    }
                                    this.email = newEmail;
                                    }

                                    public void setPassword(String rawPassword,
                                    PasswordHasher hasher) {
                                    this.passwordHash = hasher.hash(rawPassword);
                                    }

                                    public boolean isActive() {
                                    return active;
                                    }

                                    public void deactivate() {
                                    this.active = false;
                                    }

                                    // No getPasswordHash() — no one needs it
                                    }

Notice that I don't expose the password hash at all. The user object handles password changes itself, using a hashing strategy that can be swapped out later. The active flag is only modifiable through deactivate(), which gives me a place to add audit logging later. Encapsulation isn't about being secretive; it's about being intentional about what you expose and how.

The second benefit of encapsulation is that it reduces the ripple effect of changes. If I change the internal representation of passwordHash from a String to a custom Password object, the rest of the codebase is unaffected because no one outside the class was accessing it directly. This is the superpower of encapsulation.

Abstraction: Seeing the Forest, Not Just the Trees

If encapsulation is about hiding details from the outside, abstraction is about hiding details from the inside. An abstract class or an interface defines a contract without specifying the implementation. This allows you to work at a higher level of thinking.

I used to write code like this: 

public class EmailService {
                                    private SmtpClient smtp = new
                                    SmtpClient("smtp.example.com", 587);

                                    public void sendWelcomeEmail(String to) {
                                    // SMTP-specific code...
                                    }
                                    }

The problem with this code is that it ties the EmailService to a specific SMTP implementation. If I need to switch to a different email provider, or mock the email service in tests, I have to change the EmailService itself.

Abstraction solves this: 

public interface EmailSender {
                                    void send(String to, String subject, String
                                    body);
                                    }

                                    @Service
                                    public class EmailService {
                                    private final EmailSender emailSender;

                                    public EmailService(EmailSender emailSender) {
                                    this.emailSender = emailSender;
                                    }

                                    public void sendWelcomeEmail(String to) {
                                    emailSender.send(to, "Welcome",
                                    "Thanks for joining!");
                                    }
                                    }

Now, EmailService depends on an abstraction (EmailSender), not a concrete implementation. I can provide a SmtpEmailSender, a SendGridEmailSender, or a MockEmailSender for tests. This is the essence of the Dependency Inversion Principle, and it makes the code more flexible, testable, and maintainable.

Abstraction also helps with the single responsibility principle. Each class should have one reason to change. By extracting interfaces, I can split large classes into smaller, focused ones that communicate via well-defined contracts.

Inheritance: A Double-Edged Sword

No OOP topic is more controversial than inheritance. When I was a beginner, I thought inheritance was the crown jewel of OOP. I created deep hierarchies: Vehicle → Car → SportsCar → ElectricSportsCar. It felt elegant until I had to add a Bicycle that didn't have an engine, or a SelfDrivingCar that shared logic with both Car and Robot. My hierarchy collapsed under its own rigidity.

The problem with inheritance is that it creates a tight coupling between the parent and child classes. Changes to the parent ripple down to all children. Overriding methods requires careful consideration of the parent's implementation. And multiple inheritance (which Java wisely avoids) leads to the diamond problem.

Today, I treat inheritance as a tool to be used sparingly. I follow these rules:

  • Use inheritance only for "is-a" relationships. A Dog is an Animal. That's fine. A UserService is not a BaseService — that's a misuse.
  • Prefer composition over inheritance. Instead of extending a class, hold a reference to it and delegate calls. This is more flexible and doesn't lock you into a hierarchy.
  • Keep hierarchies shallow. Two or three levels maximum. Anything deeper becomes hard to understand and maintain.

Here's an example of composition over inheritance: 

public class ElectricSportsCar {
                                    private final Car car;
                                    private final ElectricEngine engine;

                                    public ElectricSportsCar(Car car,
                                    ElectricEngine engine) {
                                    this.car = car;
                                    this.engine = engine;
                                    }

                                    public void drive() {
                                    car.accelerate();
                                    engine.start();
                                    // ... 
                                    }
                                    }

This approach gives me the same capabilities without the rigid coupling. I can change the Car or ElectricEngine independently, and I can reuse them in other contexts. Inheritance is powerful, but it's also dangerous. Use it with intention and restraint.

Polymorphism: The Great Unifier

Polymorphism is what makes OOP truly powerful. It allows different classes to be treated through a common interface, with each class providing its own implementation. This is the foundation of the Open/Closed Principle — classes should be open for extension but closed for modification.

I remember the day I truly understood polymorphism. I was working on a payment processing system. I had different payment methods: credit card, PayPal, and bank transfer. Each had its own validation and processing logic. My initial solution was a giant if-else chain that checked the payment type and called the corresponding methods. It was ugly and grew with each new payment method.

Polymorphism showed me a better way: 

public interface PaymentProcessor {
                                    PaymentResult process(PaymentRequest request);
                                    }

                                    @Component
                                    public class CreditCardProcessor implements
                                    PaymentProcessor {
                                    @Override
                                    public PaymentResult process(PaymentRequest
                                    request) {
                                    // Credit card specific logic
                                    }
                                    }

                                    @Component
                                    public class PayPalProcessor implements
                                    PaymentProcessor {
                                    @Override
                                    public PaymentResult process(PaymentRequest
                                    request) {
                                    // PayPal specific logic
                                    }
                                    }

                                    @Service
                                    public class PaymentService {
                                    private final Map<PaymentType,
                                    PaymentProcessor> processors;

                                    public PaymentService(List<PaymentProcessor>
                                    processorList) {
                                    this.processors = processorList.stream()
                                    .collect(Collectors.toMap(
                                    p -> p.getType(), Function.identity()
                                    ));
                                    }

                                    public PaymentResult process(PaymentRequest
                                    request) {
                                    PaymentProcessor processor =
                                    processors.get(request.getType());
                                    if (processor == null) {
                                    throw new UnsupportedPaymentException();
                                    }
                                    return processor.process(request);
                                    }
                                    }

To add a new payment method, I simply create a new class that implements PaymentProcessor. I don't have to touch the existing code. The system is open for extension but closed for modification — exactly what polymorphism enables.

Polymorphism also makes code more readable. The PaymentService is small and focused. It doesn't need to know the intricacies of each payment method. It just delegates to the appropriate processor. This separation of concerns is what makes large systems manageable.

Composition Over Inheritance: The Hard-Won Lesson

The principle of composition over inheritance is one of the most important lessons in my OOP journey. I learned it the hard way after building a class hierarchy that collapsed under its own weight. The project was a GUI framework, and I had a base Component class with dozens of subclasses: Button, TextField, Panel, Window, etc. Adding a new feature like tooltips required modifying the base class and all its subclasses. It was a nightmare.

Composition offers a better solution. Instead of inheriting behaviour, you compose it from smaller, focused objects. 

public class Button {
                                    private final Renderer renderer;
                                    private final ClickHandler clickHandler;
                                    private final Tooltip tooltip;

                                    public Button(Renderer renderer, ClickHandler
                                    clickHandler, Tooltip tooltip) {
                                    this.renderer = renderer;
                                    this.clickHandler = clickHandler;
                                    this.tooltip = tooltip;
                                    }

                                    public void render() {
                                    renderer.render(this);
                                    }

                                    public void click() {
                                    clickHandler.handle(this);
                                    }

                                    public void showTooltip() {
                                    tooltip.show(this);
                                    }
                                    }

Now the Button class is a container of behaviours. I can change the rendering strategy, the click logic, or the tooltip behaviour independently. I can even reuse these behaviours in other components like Checkbox or Image. This is far more flexible than a rigid inheritance hierarchy.

In practice, I almost always prefer composition. It leads to smaller, more focused classes that are easier to test and understand. Inheritance is still useful for the Template Method pattern or for framework extension points, but it's no longer my default choice.

SOLID Principles: The Bridge Between Theory and Practice

All of these ideas — encapsulation, abstraction, polymorphism, composition — are distilled in the SOLID principles. I didn't fully appreciate them until I had made every mistake they were designed to prevent. But once I internalised them, my code changed dramatically.

  • Single Responsibility: A class should have only one reason to change. I used to write "God classes" that did everything. Now I split them into focused UserRepository, UserValidator, and UserNotifier classes.
  • Open/Closed: Open for extension, closed for modification. I use interfaces and dependency injection to allow new behaviour without touching existing code.
  • Liskov Substitution: Subtypes must be substitutable for their base types. I avoid overrides that break the parent's contract. If a Square extends Rectangle, it must behave like a rectangle.
  • Interface Segregation: Many client-specific interfaces are better than one general-purpose interface. I split large interfaces like UserService into UserReader, UserWriter, and UserAdmin.
  • Dependency Inversion: Depend on abstractions, not concretions. I use constructor injection with interfaces, making my code more testable and flexible.

These principles aren't rules to be followed blindly. They're guidelines that help you think about the structure of your code. The best code I've written follows them naturally because the design emerged from careful thought, not from a checklist.

Writing OOP Code That Breathes

Over the years, I've developed a sense of what good OOP code feels like. It's not just about satisfying a linter or passing tests. It's about a quality that's hard to quantify but easy to recognise: the code breathes.

Code that breathes is easy to navigate. You can open a class and immediately understand its purpose. The methods are short and named well. The dependencies are clear and minimal. Adding a new feature feels natural, not like forcing a square peg into a round hole.

I've learned to cultivate this quality through practice and discipline. I refactor relentlessly. I rename variables and methods until they feel right. I extract classes when a class grows too large. I write tests that document the behaviour. I ask myself: "If I came back to this code in six months, would I be able to understand it quickly?"

One practice that has helped immensely is reading other people's code. I've studied open-source projects like Spring Framework and JUnit. I've seen how expert developers organise their code. I've adopted their patterns and adapted them to my own style. You can't become a good writer without reading good writing, and the same is true for code.

Another practice is pair programming. Explaining my design choices to another developer forces me to articulate the why. It exposes gaps in my reasoning and leads to better designs. The best code I've written came from conversations, not from sitting alone in a room.

My OOP Journey Never Ended

I often joke that I've been learning OOP for ten years and I'm still a beginner. The truth is, every project teaches me something new. A new problem forces me to think in a new way. A new language feature opens up possibilities I hadn't considered. The journey never ends, and that's exactly why I love it.

I've also learned that OOP doesn't exist in a vacuum. Today, I often mix OOP with functional concepts — using Streams and lambdas in Java, or immutable data structures. The lines between paradigms are blurring, and that's a good thing. The best solution uses the right tool for the job.

But the core lessons of OOP remain invaluable. Encapsulation, abstraction, polymorphism, and composition are timeless ideas. They help us manage complexity, build testable systems, and write code that doesn't rot. They are the foundation upon which I build everything.

"The best OOP code looks like a well-written story — coherent, purposeful, and impossible to put down."

My advice to anyone starting their OOP journey is this: don't memorise definitions. Build things. Break them. Fix them. Build them again. Each time you'll understand a little more. And one day, you'll open a file and realise that the code you wrote feels alive. That's when you know you've truly understood OOP from first principles.

Final Thoughts

Understanding OOP from first principles is not about mastering a checklist of features. It's about embracing a mindset — a way of thinking about problems and solutions that prioritises clarity, flexibility, and resilience. It's about recognising that software is a living thing, and that the structure we give it determines how well it can grow and adapt.

I've made countless mistakes in my OOP journey. I've written classes that were too big, hierarchies that were too deep, and abstractions that were too clever. But each mistake taught me something valuable. Each refactor made me a better developer. And each project reminded me why I love this craft.

If there's one thing I want you to take away from this article, it's this: OOP is not about the language; it's about how you organise your thinking. The classes, interfaces, and methods are just tools. The real power comes from how you use them to model the world and solve problems.

So go out there and build something. Make mistakes. Refactor. Learn. And enjoy the journey. Because the journey is the best part of being a software engineer.
